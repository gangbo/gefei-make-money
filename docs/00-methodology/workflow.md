# 从资料到项目：阶段与归档规则

## 目录职责

| 位置 | 放什么 | 不代表什么 |
| --- | --- | --- |
| `../01-sources/` | 榜单快照、来源笔记、社区原话摘要、竞品观察、导出文件 | 收集到资料不代表需求通过 |
| `../02-candidates/` | 从资料提取的任务、人群、付费线索、候选台账 | 有候选不代表值得开发 |
| `../03-feasibility/` | 市场可进入性、输入获取、开发和运营成本、交付与获客难度 | 程序能运行不代表产品能盈利 |
| `../04-validation/` | 有限实验、原型、真实使用/付款结果、复盘 | 模拟输入不能当客户验收 |
| `../projects/` | 用户已有产品及经营记录 | 不混入新项目候选 |
| `../operations/` | 运营、推广与外链资料 | 与需求阶段分开 |
| `../grow-seo-traffic/` | 原有 SEO 专项数据与报告，保留固定路径 | 历史数据不自动代表当前市场 |

这是四个阶段，不要求每条资料都走完。可以直接排除重复项目，也可以把候选退回补证据。历史文件不随候选状态反复搬家，使用稳定 ID 关联。

## 阶段 1：采集资料

先查[来源索引](../01-sources/INDEX.md)。按来源、数据周期、采集日期、过滤条件去重。文件夹按实际采集日期组织，文中另写数据所代表的月份或周期。

每份资料记录：来源 URL、采集日期、数据周期、查询/筛选条件、读取范围、内容类型、已知限制、关联候选 ID。采集后登记索引。

来源状态：未采集 / 部分采集 / 本批已采集 / 受阻。`本批已采集`只代表列出的范围，不代表整个网站都研究完。

正文摘要不是原始文件。保留原始导出或截图时原样保存，解释写到伴随的 Markdown。只有摘要时直接写“人工摘要”，不冒充完整快照。

## 阶段 2：提取需求

从来源写出“谁在什么情境下，需要完成什么任务”，分配 `D-001` 形式的稳定 ID。不能只抄产品名或收入数字。使用[候选模板](../02-candidates/template.md)，登记[候选台账](../02-candidates/INDEX.md)。

进入可行性阶段需至少有具体任务、可追溯的需求/付费线索和明确的待验证问题。证据缺少时记待补证据，不用主观评分掩盖空白。

## 阶段 3：判断我们能否低成本做

逐项检查：

1. 是否已有同类自有产品，用户是否已试过此方案。
2. 是否能低成本取得有代表性的输入，自己判断结果质量。
3. 能否自助完成，不依赖逐单修图、诊断或沟通。
4. 开发时间、单次处理、重试、支持和维护成本；未知数字标未知。
5. 市场是否有足够付费需求；是否有可核查的获客入口。
6. 现有竞品如何完成任务，我们具体改善什么；有竞品不直接淘汰。

状态统一为：待筛选 / 待补证据 / 待实验 / 暂缓 / 已停止 / 已有产品 / 已立项。只有决策与证据满足时才改状态。本仓库目前没有通过筛选的新项目。

## 阶段 4：做有限验证

先定义假设、输入来源、对照、成本上限、成功/停止条件。实验结果记录失败、人工介入和使用/付款事实。模拟样本、厂商演示和真实客户样本分开。

当前条件不要求联系客户或访谈作为前置步骤。优先可自行取得输入、公开可观察结果的验证。不能用这个偏好替代最终真实使用与付款证据。

## 每次对话结束的更新顺序

保存新资料 → 更新来源索引 → 更新候选台账 → 写入决策记录 → 更新 STATUS 的已做/待做/停止事项。没有新增研究时只更新相应进度，不重新抓数据。

过往资料是否刷新按用途决定：价格、产品功能和当前市场决策需要核实；历史月度榜单保持原快照，新增月份另存。不要每次打开对话就重查所有来源。
