# 自然搜索增长

遵循一个不可颠倒的流程：

`询问并获取数据 → 判断数据是否足够 → 基于数据分析 → 结合项目现状制定或实施优化 → 记录并复查`

把本 Skill 目录复制到其他项目后直接使用。不要继承来源项目的品牌、域名、框架、路由、市场、数据或结论。

## 核心规则

1. **先列数据清单。** 每次任务都先创建或更新
   `docs/grow-seo-traffic/data-checklist.md`，完整列出当前决策需要的数据、已有项、缺失项、时间范围和用途。
2. **先问数据，后分析。** 告诉用户还需要哪些数据，并允许用户用任何方便的方式提供。可以使用用户授权的浏览器、连接器或公开来源代为获取。
3. **不限制格式。** 接受导出文件、电子表格、截图、PDF、JSON、HTML、粘贴文本、链接、API 响应、录屏或其他可理解资料。不要要求用户转换成指定格式。
4. **数据不足就停止。** 必需数据缺失、时间范围太短、过滤条件不清或截图无法读清关键值时，只继续获取数据或提出精确问题，不输出机会判断和优化建议。
5. **保存原始资料。** 把获得的数据按原样保存到
   `docs/grow-seo-traffic/raw/YYYY-MM-DD/<source>/`；不要覆盖旧批次。无法直接保存的浏览器信息，用截图或带来源、时间和口径的笔记保存。
6. **数据清单不能省略。** 即使数据由 Agent 自动获取，也要在清单中记录来源、覆盖周期、市场、设备、过滤条件、保存位置和是否足够。
7. **数据够了再读项目做完整分析。** 把搜索数据与目标项目自己的代码、路由、页面、文案、产品能力、部署方式和线上表现结合起来，不能只看报表。
8. **来源分开。** Google、Bing、第三方估算和站内分析分别计算和解释，不把不同口径拼成一组指标。
9. **保护已有流量。** 没有明确证据、验证方法和回滚方案时，不修改已有点击页面的 URL、canonical、title、H1 或主要意图。
10. **主动提供获取方式。** 不要只让用户自己导出。优先检查是否有专用连接器或 API；否则询问是否允许使用
    Computer Use 从用户已登录的 GSC、Bing Webmaster Tools、Semrush、Google Trends 等页面只读获取。
    用户已经明确要求“帮我获取”时视为已授权，不重复询问。

## 第一阶段：询问并获取数据

先确定这是已有搜索历史的站点还是新站，并判断用户想解决的是流量表现、索引、内容机会还是实验复查。然后完整阅读
[数据需求与充分性](references/data-requirements.md)，检查项目中已有的
`docs/grow-seo-traffic/`，创建数据清单。

第一次回复用户时：

1. 列出完整数据清单；
2. 标出最先需要用户提供的 1–3 个阻塞项；
3. 对每项说明平台、建议时间范围、需要看到的维度或字段，以及它会影响什么判断；
4. 明确说明格式不限；
5. 给出两种选择：用户直接提供，或由 Agent 代为获取；
6. 对需要登录的平台，询问：“是否允许我使用你已登录的浏览器，只读查看并把相关数据保存到项目中？”；
7. 如果可通过连接器、API、用户现有浏览器会话或公开网页获取，在获得所需授权后主动执行。

用户已经提供数据时不要重复索取；先保存、阅读并更新清单，再判断还缺什么。

详细获取方式见 [数据来源](references/data-sources.md)。
Semrush 关键词与长尾词研究要额外遵循 [Semrush 工作流](references/semrush-workflow.md)。

### 使用 Computer Use 获取

用户允许代为获取后，加载 `computer-use:computer-use` 并遵循其操作规范：

- 优先使用更专用的连接器或 API；没有合适工具时再操作浏览器；
- 使用用户已有登录状态，只做导航、读取、筛选、导出和截图；
- 不修改站点资源、平台设置、用户、权限、sitemap 或其他外部状态；
- 每次确认站点资源、目标市场、日期范围、设备和过滤条件；
- 获取 Semrush 数据时默认使用代理入口 `https://zh.semrush.fast.wmxpro.com/`；目标项目或用户明确指定
  其他入口时再改用其他入口；
- Semrush 不只查域名已有排名。涉及关键词机会或长尾词时，必须用 Keyword Overview / Keyword Magic
  查询 seed 词、Trends 起势词和竞品/用户语言变体，记录搜索量、KD、意图、SERP features、匹配类型和问题词；
- 用户要求竞品、SERP 或关键词机会时，必须把“实时 SERP 前排页面 → 截图/文本保存 → 竞品域名或 URL 的
  Semrush Organic Positions / Top Pages → 竞品关键词抽取 → 机会归类”作为独立数据链路执行；不能只查询
  目标站点，也不能只凭搜索结果摘要下结论；
- 下载或截图后保存到 `docs/grow-seo-traffic/raw/YYYY-MM-DD/<source>/`，同步更新数据清单；
- 未登录或会话失效时请用户自行登录，不索取密码；遇到验证码时交给用户完成。

### 获取 X 平台近期数据

当关键词研究、用户用语、痛点、热点或竞品讨论需要近期 X 信号时，加载全局
`$xai-call-grok`，启用 `x_search`：

1. 从 GSC、Bing、Semrush、Trends、产品功能和竞品名称中整理关键词簇；
2. 为每个关键词簇补充用户问题词、使用场景词、替代方案词和目标语言变体；
3. 分关键词簇搜索，不把所有主题塞进一次查询；
4. 对“近期”设置明确的 `from_date` 和 `to_date`；
5. 要求返回作者、发布日期、帖子链接、主要观点和重复出现的主题；
6. 保存查询关键词、日期范围、提示、结果与链接到
   `docs/grow-seo-traffic/raw/YYYY-MM-DD/x/`，同步更新清单。

如果没有 `XAI_API_KEY`，请用户在本机环境中设置，不让用户在对话里粘贴完整密钥。X 帖子只作为用户语言、
需求和选题信号，不能替代第一方搜索数据、关键词需求数据或官方事实来源。样本不足时如实标记，不用模型常识
补造成近期讨论。

## 第二阶段：判断是否足够

逐份阅读实际资料，不根据文件名或扩展名判断。检查：

- 来源是否可信；
- 时间范围是否覆盖当前问题；
- 市场、语言、设备和过滤条件是否明确；
- 关键数字或页面是否能可靠读取；
- 不同文件口径能否比较；
- 已有站点是否仍缺少会改变结论的第一方数据；新站是否已有足够的需求与 SERP 证据。

在 `data-checklist.md` 中把每项标记为 `ready / partial-ready / missing / unclear / unavailable`，并写明理由。

只要任一必需项不是 `ready`，就保持“数据不足”，不要进入第三阶段。若某项是 `partial-ready`，只能进入它能支撑的有限分析范围，并明确哪些判断仍不能做。用户确认无法提供某项时，如果它会阻塞结论，就如实停止；不要用经验猜测填补。

确认是没有历史数据的新站时，不要求虚构第一方表现；改用项目目标、当前实现、关键词需求和实时 SERP
建立上线前研究基线，并明确记录“暂无第一方表现数据”。

## 第三阶段：结合数据和项目现状分析

数据足够后：

1. 建立各来源独立的流量、查询、页面、CTR、排名或索引基线；
2. 找出必须保护的页面和已经验证的搜索意图；
3. 识别有展示但点击低、排名接近首页、内容与查询不匹配、关键词蚕食和索引异常；
4. 检查实时 SERP 与真正的搜索竞品；
5. 阅读目标项目代码和线上页面，核对 metadata、canonical、hreflang、robots、sitemap、结构化数据、内部链接、页面文案和工具体验；
6. 判断项目实际产品能力能否满足目标搜索意图；
7. 把事实、推断和不确定性分开，每个重要结论引用保存的数据来源。

需要技术 SEO 复核时完整阅读 [技术 SEO 验证](references/technical-verification.md)；需要排列机会池时完整阅读 [机会评分方法](references/opportunity-scoring.md)。

## 第四阶段：制定或实施优化

根据用户请求决定交付深度：

- 用户只要求分析：给出按优先级排序的优化方案，不修改代码；
- 用户要求优化或实施：完成一个可独立验证的最小批次，运行相关测试并检查线上输出；
- 涉及删除已索引页面、修改 URL/canonical、批量 noindex 或高流量页面核心意图时，先获得明确确认。

把分析、改动、依据、上线日期、观察指标和复查时间保存到
`docs/grow-seo-traffic/reports/`。后续复查必须重新获取覆盖上线前后窗口的数据，不能只看短期波动。

## 输出要求

数据不足时只输出清单状态、缺失数据、提供方式和受影响的判断，不输出 SEO 结论。

数据充足时包含数据覆盖、各来源独立基线、需保护页面、机会优先级、项目现状、建议或已实施改动、验证结果、观察周期和成功标准。
